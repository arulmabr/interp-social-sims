2. THE PROMPT DEFECTS -- THE MOST IMPORTANT SECTION
--------------------------------------------------------------------------------
Asked late in the session whether the prompts matched the paper. They did not.
Three separate defects, found in sequence, each invalidating work already done.

2.1 OPTION ORDER RELABELLED THE OPTIONS INSTEAD OF REORDERING THEM  (BD28)
    Every order-1 legacy prompt read:
        Safe Option: a 25% chance of $37 and otherwise nothing
        Risky Option: $20 for sure
    body_text paired each label with a POSITION rather than with its lottery, so
    the gamble was announced as "Safe Option" and the sure amount as "Risky
    Option". z stayed content-anchored, so nothing was inverted, but half of
    every legacy comparison was asking a different question.
    THIS INVALIDATED BD27. cos(g1,g2) = -0.814 had been reported as evidence
    that the readout gradient is predominantly a position direction. The simpler
    explanation is the bug: the word naming the gamble flips between orders, so
    a model with any prior toward "Safe" has its z-raising direction flipped.
    The measurement cannot separate the two, so the claim was withdrawn rather
    than qualified.

2.2 THE LABELS, CURRENCY AND GRID DIVERGED FROM THE PLAN FOR NO REASON  (BD29)
    ICLR_PLAN.md:153 specifies legacy "Safe/Risky" and neutral "A/B".
    Probes/tasks/prompts.py denominates everything in TOKENS.
    This code had "Safe Option"/"Risky Option", "Option A"/"Option B", dollars.
    None of it was a decision; it was written without checking the spec and
    never recorded as a deviation.
    THE NEUTRAL DIVERGENCE CAUSED A BUG I THEN "DISCOVERED". "Option A" and
    "Option B" share their first token, so z = log p(Option) - log p(Option) = 0
    on every neutral trial, and half the B3.1 gradient prompts contributed
    exactly zero. I reported that as a finding about the readout and built a
    per-label-set stem to work around it. The plan's "A"/"B" tokenise
    distinctly ([32,362] vs [33,426]); the fix was to use the specified labels.

2.3 THE SOCIAL GAMES HAVE NO GAME TEXT, AND FREE TEXT IS NOT FREE TEXT  (BD31)
    Found by reading the rendered prompt audit. A responder trial renders as
        Reject: nothing
        Accept: 90 tokens for sure
    All three legacy stacks state the proposer, the pie, and that rejection
    gives BOTH parties zero. Track B states none of it. Without the framing,
    rejecting a low offer is an arithmetic error rather than inequity aversion,
    and the mini-ultimatum's alternatives never reach the model at all.
    Separately, ICLR_PLAN.md:153 says free text is "scored by sequence
    log-probability"; both response formats use the same first-token readout,
    so "freetext" is a second multiple-choice arm in different wording.
    Author replied "audit ok" with these known. Recorded in B_DEVIATIONS.md with
    a standing caveat: NO SOCIAL NUMBER FROM THIS BUILD MAY BE REPORTED AS A
    SOCIAL PREFERENCE. Nothing in the current chain reads them.

2.4 WHY EVERY TEST PASSED THROUGH ALL OF THIS
    The suite compared the code against itself. `risky_label` agreed with
    `body_text` because both applied the same wrong rule; no test ever read a
    rendered prompt. The check that finally caught it compared the RENDERED
    PROMPT against what the readout claimed to be scoring -- an external
    consistency check, not an internal one. reports/B_PROMPT_AUDIT.md now
    renders 1,248 prompts across 624 cell types verbatim after the chat
    template, with the exact token ids scored per label, and a test asserts from
    the rendered text alone that each label names the right option.

2.5 "CONSISTENT WITH THE PAPER" HAS NO SINGLE ANSWER  (BD32, corrects BD29)
    | stack              | wording                  | answer tokens | grid        |
    | Probes             | SAFE VS. RISKY, numbered | 'Safe'/'Risky'| 20..240 (45)|
    | SAE                | prose                    | safe/risky    | 10..180 (35)|
    | Revised Prompting  | prose + CoT              | safe/risky    | 10..180 (35)|
    Common to all three: safe = 50 tokens, p = 0.5, tokens, EV crossover at 100.
    BD29 asserted the published grid "is" 20..240 and the plan simply wrong.
    In fact 20..240 is the PROBE stack's grid; the SAE stack -- which produced
    the paper's headline layer-50 SAE results -- used 10..180. ICLR_PLAN.md's
    10..240 is the union of the two. Which grid the bridging cell should
    reproduce depends on which figure it bridges to. AUTHOR DECISION; the build
    currently uses 20..240 by my choice, not by instruction.

4. B2 -- ESTIMATOR AND GATE                     STATUS: FAILED, TO BE RE-RUN
--------------------------------------------------------------------------------
GATE B2 FAILED in all 18 configurations, both before and after the author's
restructure. All of these numbers predate the prompt fixes and are withdrawn;
they are recorded because the REASONS survive the rebuild.

After the author's items 2 and 3 (Gate B2 on alpha and gamma only; misspecified
agents become BASES crossed with interventions):
    alpha RMSE 0.0091, gamma 0.0044   (limit 0.05)          PASS
    lambda RMSE 0.416                 (limit 0.15)          FAIL -> own gate
    CPT preference classified          0.70                 FAIL (needs 0.95)
    every non-preference intervention  0.00                 PASS (perfect)
    misspecified model-free accuracy   9 of 10 cells at 1.00

THREE ESTIMATOR CORRECTIONS, each found by the study failing for the wrong
reason (BD14):
  * no per-template intercept -> template variation was unmodelled misfit that
    decided the model comparison. Preference share 0.265 -> 0.591.
  * the fit used binary choices when the readout returns z. Fitting z took
    alpha's RMSE from 0.055 to 0.0054 and the preference share to 1.000.
  * D5 divided two squashed probability differences and failed genuine
    preference shifts on noise alone; it now uses mean dz.
No threshold was ever touched; plan v4's numbers live in one place and a test
asserts them.

TWO BASE AGENTS WERE BROKEN, BOTH SCALING FAULTS (BD22, BD24)
  * the monotone base was INDIFFERENT on every trial: z sd 0.0073, P(risky)
    spread 0.0105. The contextual-utility range was measured in dollars for
    every family, but that family's utility is a bounded tanh.
  * the mean-variance base was SATURATED: z to -90.32, sd 10.27. mean - b*var
    is not scale-invariant (variance grows as the stake squared). Switched to
    mean - b*SD.
  A degenerate base passes every specificity check for free, so both would have
  read as the misspecification test working.

STRUCTURAL FINDING THAT SURVIVED THE RESCALING (BD25)
  On a mean-SD base a preference change is observationally an ACTION BIAS.
  After contextual normalisation the risk term is sqrt(p(1-p)), with no
  dependence on the reward level, so the shift is nearly constant in z:
  dz mean -0.2611, sd 0.0753 (ratio 0.29) against a CPT alpha shift's 0.99,
  which changes sign across x. The model-free separation of preference from
  action is MODEL-DEPENDENT. Reported, not fixed: fixing it would mean handing
  the classifier the answer.

LAMBDA: NO GRID IN THE SWEPT FAMILY IDENTIFIES IT  (BD26)
  24 grids, 576 to 18,432 mixed rows. With alpha and gamma free, RMSE PLATEAUS
  at about 0.26 and gets WORSE with density (0.2695 -> 0.3206) because each new
  mixed trial adds alpha/lambda confounding faster than lambda information.
  With alpha and gamma HELD at the baseline fit it improves monotonically and
  PASSES at 12,288 mixed rows (2.01x the B1 grid), RMSE 0.1487.
  => lambda is identifiable only if alpha is pinned on the gain frame, and then
     needs about twice the grid. "Buy more mixed trials" alone is the wrong
     purchase. Predicted before fitting in BD10: lambda cancels EXACTLY outside
     mixed frames (max |dz| = 0.000000 across all 490 single-sign trials).

NUMERICAL NOISE  (author item 3)
  B2-cal measured it directly: five repeat unbatched reads, BIT-IDENTICAL,
  max_abs_range = 0.0. So the primary recovery configuration is numerical noise
  0, with 0.1 and 0.25 kept as sensitivity rows labelled "batched reads only".
  This matches the Friday session's D50: the floor is not stable across
  allocations (0.094 in one 70B run, 0.000 in another).

DOMINATED-TRIAL POLICY  (BD9, decided before any fit)
  "exclude" beats "lapse" on alpha (0.0091 vs 0.0111), lambda (0.416 vs 0.661)
  and the classification rate the gate reads (0.70 vs 0.50). Default stands.

    against z sd 4.84 -- the CPT fit is poor at low p, not merely oddly

6. THE ANCHORS (B3)
--------------------------------------------------------------------------------
B3.1 GRADIENT -- ran on the 70B, conclusion withdrawn, to be re-run.
  Completed in 8:40 on 4 GPUs. Ten directions at layers 48 and 50 with sha256
  each and a how_to_load block. Gradient taken w.r.t. the OUTPUT of
  model.model.layers[L], which is the tensor SteeringHook adds to -- a gradient
  taken anywhere else would not be the direction a dose moves.
  Per-order decomposition (author item 4): g1, g2, g1+g2 (order-invariant
  anchor), g1-g2 (position-bias control), and one-format for the Friday
  session's G4b.
  cos(g1,g2) = -0.814 (L48), -0.823 (L50). REPORTED AS A FINDING, THEN
  WITHDRAWN: the option-order bug relabels the options between the two orders,
  so the measurement cannot separate a position effect from the relabelling.
  Within-order coherence was 0.927-0.941, so each direction was real.
  An 8B dry run caught a real bug first: freezing every parameter left nothing
  in the graph requiring grad, so retain_grad raised. Fixed with
  enable_input_require_grads.

B3.2 LoRA -- built, never run on the 70B, has not passed cloning on the 8B.
  Three adapters per A5 (reference at theta0, alpha-shifted, bias-shifted),
  identical data order and schedule, one loaded base switched with set_adapter.
  Loss is soft-label cross-entropy over the full vocabulary at the answer token.
  Trains on disc+cal so the selection split is genuinely held out.
  Cloning bar: correlation >= 0.95 AND calibration slope 0.9-1.1.
  THREE DRY RUNS, NONE PASSED:
    v1  lr 1e-4, 300 steps  loss 0.81->0.31  r 0.976  slope 0.714   FAIL
    v2  lr 3e-4, 600 steps  loss 0.83->0.74 FLAT  r 0.000  slope 0.000  COLLAPSE
    v3  lr 1e-4, slope curve every 250 steps:
            step 250  r 0.966  slope 0.821  z_sd 4.165
            step 500  r 0.976  slope 0.704  z_sd 3.534
  v2 was MY ERROR: v1's evidence pointed only at step count, and I raised the
  learning rate as well to try to shorten the eventual 70B run. At 3e-4 the loss
  never fell and the adapters learned nothing. Cost ~21 min of 8B GPU and about
  an hour of wall clock.
  v3 shows the slope moving AWAY from the bar with more training, which kills
  the under-training hypothesis. A plausible mechanism is that soft-label CE has
  a vanishing gradient at saturated targets, so extreme-z trials contribute
  almost nothing and the model never learns the full range.
  v3 was cancelled mid-flight when the prompt bug was found -- it was training
  on contradictory prompts.
  Author item 4 sets the order of investigation: re-measure the slope curve on
  corrected prompts, reporting TRAIN-SET slope beside HELD-OUT slope at every
  probe. If held-out < 0.9 while train ~ 1 it is generalisation (more prompts,
  weight decay, lower rank, checkpoint selection), and only if the train slope
  also stays below 0.9 is the objective at fault.

7. INFRASTRUCTURE BUILT ALONG THE WAY
--------------------------------------------------------------------------------
CHECKPOINT AND RESUME  (BD21, BD33)
  Slurm jobs already survive a dropped connection; they do not survive
  preemption, and ou_bcs_low/mit_preemptable are preemptible. Every long job now
  resumes: an append-only on-disk array flushed every chunk, written atomically
  via temp-and-rename so a kill mid-flush leaves the previous good checkpoint.
  numerics_fp32 additionally skips a finished dtype stage (so a requeue after
  fp32 does not pay 346 s to reload it); a recovery array task whose output
  exists returns immediately; LoRA training checkpoints adapter and optimizer
  state every 25 steps.
  TESTED BY INTERRUPTION, not by assertion: test_resume_integration.py crashes
  the real read loops mid-pass and asserts they resume to the IDENTICAL answer
  and do not redo finished work.
  A LATENT BUG FOUND WHILE VERIFYING: the no-checkpoint branch built a Partial
  over /dev/null.npz and raised PermissionError the moment anyone took it.
  A REAL BUG FOUND BEFORE THE RERUN: a checkpoint keyed on trial ids would have
  silently reused stale reads after the prompt rewrite. A trial_id hashes
  content and format but NOT the words shown to the model, so renaming labels
  left every id identical while every prompt differed. The resume would have
  declared all 872 rows done and returned the old run's z. items_key now folds
  the rendered prompt text into the key.

FAILURE WATCHDOG
  A Monitor polling every 60 s, reporting new job failures, preemptions,
  completions, error signatures in logs, and stalled heartbeats. Built badly
  twice first: version 1 replayed 12 hours of history and called my own
  deliberate cancellations failures; version 2 flagged the heartbeats of
  COMPLETED jobs as hangs because it asked "is anything running" rather than
  "is THIS job running". Both were the same shape of mistake -- a global check
  where a per-job one was needed.

8. SLURM AND PLACEMENT -- LESSONS PAID FOR
--------------------------------------------------------------------------------
  * GPUs were often free while my jobs sat PENDING. The causes were mine:
    over-large memory requests (128-256 GB when a 70B needs ~20-40 GB of host
    RAM), the wrong QOS (--qos=normal instead of mit_amf_advanced_gpu, which
    tripped a per-user CPU cap filled by an unrelated project), and submitting
    to a partition that looked large (mit_preemptable: 1,038 GPUs) but had 1,043
    jobs queued.
  * A generic --gres=gpu:N gets PINNED to a specific card type (l40s), which
    silently narrows eligibility. It also nearly OOMed the 70B gradient: pinned
    to l40s:2 = 96 GB for a model needing ~141 GB.
  * The 8B LoRA sat 17 minutes on mit_preemptable without being placed; moving
    it to mit_normal_gpu started it in seconds.
  * RULE ADOPTED: measure free capacity per card type before submitting, request
    the type explicitly, and move a job that has not started in ~5 minutes.
  * Compute nodes cannot see the session scratchpad; helper scripts must live in
    the repo.
